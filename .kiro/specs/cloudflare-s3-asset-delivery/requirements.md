# Requirements Document

## Introduction

The portfolio site at `www.crgomez.com` currently links its resume PDF, favicon, and social-preview image directly to `https://s3.us-west-2.amazonaws.com/crgomez.com/...`. That bucket grants anonymous `READ` through a bucket ACL and anonymous `s3:ListBucket` plus `s3:GetObject` through a bucket policy, has no Public Access Block configuration, and still has ACLs enabled. Anyone can enumerate the bucket and retrieve every object in it, including six objects the site never links — among them two role-targeted resume variants that the site does not publish, one of which is the owner's current resume. These requests reach S3 directly and bypass Cloudflare entirely, so the zone's WAF, caching, and analytics do not apply to them.

This feature establishes a new document delivery path: a private-by-default bucket `crgomez-content`, fronted by Cloudflare at the new hostname `field.crgomez.com`, with anonymous `s3:GetObject` allowed only on explicitly named keys and only from Cloudflare's published IPv4 source ranges. It also remediates the existing bucket to a fully private archive. The remediation and the new path are specced together because the remediation cannot complete until the site stops depending on public reads from the old bucket.

The feature also moves both Terraform configurations onto a gated Spacelift pipeline before the new delivery path is built, so that every infrastructure change after the immediate lockdown arrives as a reviewed pull request with a human-confirmed apply, and so that no long-lived AWS key or auto-approving apply workflow remains in the apply path.

The architecture is chosen partly for portfolio value: it keeps S3 versioning, object-level access logging, and presigned-URL capability for unpublished resume variants, and it makes the original public-read finding class structurally impossible on the new bucket rather than merely corrected.

This feature also corrects a content defect alongside the security remediation. The resume the site links, `crgomez-security-engineer.pdf` (2025-11-02), is nine months older than the owner's current resume, `crgomez-seceng-ir.pdf` (2026-01-31), so visitors have been downloading a stale document. The migration publishes the current document at the new hostname.

### Scope boundaries

In scope: the new bucket, log bucket, bucket policies, the Cloudflare DNS record together with the Cloud Connector rule, cache rule, and response-header transform rule that serve Delivery_Host, the zone SSL/TLS mode change, the seven site references, remediation of the existing bucket, the publish and cache-invalidation procedure, the scheduled range-drift and synthetic delivery checks, Terraform codification of what this feature creates, the Spacelift CI/CD foundation for both Terraform configurations, the migration of both Terraform states into Spacelift, retirement of the Terraform Cloud and GitHub Actions apply path in `Terraform-CF-WAF`, and the phased delivery order.

Out of scope:

- The separate finding about internal identifiers and personal contact details committed under `.kiro/specs/**` in the public repository. Greptile is now connected to the repository, so that content is also indexed by a third party, which is a further reason for the owner to address the finding separately.
- The IAM posture finding (AdministratorAccess user with a long-lived static key, missing MFA). Requirement 15 removes the dependency on that user as the apply path for this infrastructure, but reducing that user's permissions remains out of scope.
- Pinning the mutable GitHub Actions tags in the `Terraform-CF-WAF` repository as separate work. Requirement 15 removes the only workflow in that repository that carries them, and the workflows this feature adds pin actions to commit SHAs under Requirement 5.

### Resolved decisions

All previously open decisions are closed. The outcomes and reasons are recorded here and applied throughout the requirements below.

1. **Which PDF is the current resume — `crgomez-seceng-ir.pdf`.** The owner confirms `crgomez-seceng-ir.pdf` (2026-01-31) is current and that the site has been linking the older `crgomez-security-engineer.pdf` (2025-11-02) throughout. `crgomez-seceng-ir.pdf` therefore becomes the Published_Resume source object and is retained rather than deleted, reducing the Requirement 2 delete set to five objects. `crgomez-security-engineer.pdf` stays in Retained_Objects until Requirement 7 repoints Site, then becomes unreachable through the Requirement 8 final lockdown; it is kept in the Legacy_Bucket archive rather than deleted.
2. **Zone geo-block rule — kept, with no skip rule for document paths.** The owner expects no legitimate traffic from the eight listed countries, so the existing zone-level `http_request_firewall_custom` geo-block rule applies to every request to Delivery_Host, Published_Document downloads included.
3. **URL path shape — namespaced, with two prefixes.** Published_Document keys use the `docs/` prefix; the social-preview image and the favicon use the `img/` prefix, because site imagery is not a published document. Both prefixes follow the character convention in Requirement 14 criterion 4.
4. **Published filenames — role-free and date-free keys.** The published keys are `docs/resume.pdf`, `img/hero-banner.png`, and `img/favicon.png`. Requirement 14 criterion 1 makes a Published_Document URL permanent across content replacements, so a key must encode no role, date, or source filename: `docs/resume.pdf` survives a change of target role where `crgomez-seceng-ir.pdf` would not, and `img/favicon.png` replaces `amplify.png`, which names the wrong product and is cited by nothing. The human-readable download name is carried separately by the `Content-Disposition` filename parameter in Requirement 4 criterion 5, set to `carlos-gomez-resume.pdf`, which decouples the stable URL from the friendly filename. This key naming is an owner-overridable choice: changing it before implementation costs nothing, and changing it after publication breaks every citation of a published URL.
5. **Edge-to-origin mechanism — Cloud Connector, forced by the Free plan.** Zone `crgomez.com` is on the Cloudflare Free plan. Cloudflare's Origin Rules availability table lists the "Override Host header" action as unavailable on Free, Pro, and Business and available only on Enterprise, so an `http_request_origin` ruleset cannot rewrite the `Host` header for Delivery_Host on this zone. Cloud Connector is available on all plans, with a budget of 10 rules on Free, routes matching traffic to a public cloud provider bucket, and rewrites the `Host` header automatically. The delivery path therefore uses Cloud_Connector_Rule, and Requirement 6 is written against the Terraform resource `cloudflare_cloud_connector_rules`. Two consequences follow and are carried into Requirement 6: Cloud Connector applies no caching of its own, so a separate cache rule is a required companion rather than an optimization; and Cloud Connector rules are evaluated last in the request workflow and take precedence over other rules that modified the same settings, including the `Host` header. Cloudflare's own documentation page labels the feature Beta in its title while the availability table on the same page states general availability. That ambiguity is a stated risk of this decision because the delivery path depends on the feature; the fallback is a plan upgrade to obtain the Host-override action or a different origin fronting the bucket.
6. **CI/CD platform — Spacelift over HCP Terraform.** The owner chose Spacelift for its future capability. Requirement 15 defines the two stacks, gated applies, role-based AWS authentication, and the retirement of the Terraform Cloud apply path.
7. **Source-address condition — IPv4 only.** DNS shows the regional S3 REST endpoint is IPv4-only: `s3.us-west-2.amazonaws.com` returns 8 A records and 0 AAAA records, while `s3.dualstack.us-west-2.amazonaws.com` returns 8 of each. Cloudflare therefore reaches the Origin_Endpoint over IPv4 only. Cloudflare's published IPv4 prefixes are all `/13` through `/22`, narrower than the `/8` bound at which AWS evaluates an `aws:SourceIp` condition as public, so an IPv4-only condition is non-public with no transformation. Requirement 5 carries the condition and the constraint that the origin stays on the non-dualstack endpoint.
8. **How Cloudflare_Range_Allowlist reaches Terraform_AWS — a reviewed literal list committed to the repository, with a scheduled drift check.** No Cloudflare provider, data source, or API token is used in the AWS configuration. A scheduled workflow compares the committed list with Cloudflare's published list and proposes changes as pull requests. Two alternatives were considered and rejected:
   - **AWS Secrets Manager holding a Cloudflare API token, read at apply time:** rejected because it places a Cloudflare credential in the AWS apply environment and risks persisting it into Terraform state, to obtain data that is public.
   - **An `http` data source fetching Cloudflare's published ranges at apply time:** rejected because externally fetched data would change the bucket policy at apply time without a reviewed diff, so a malformed or truncated response could render a narrowed or widened condition.
9. **Terraform state — Spacelift-managed state for both stacks.** This is an owner-overridable choice. Spacelift-managed state needs no backend credential plumbing and leaves no state bucket to secure, and Spacelift's state export remains available as an exit path. Requirement 15 defines the migrations out of the Terraform Cloud workspace `terraform-cf-waf` and the S3 backend in `crgomez.com-state`.

## Glossary

- **Delivery_Host**: The hostname `field.crgomez.com`, served through the Cloudflare proxy.
- **Edge**: The Cloudflare proxy layer handling requests to Delivery_Host, including WAF rule evaluation, HTTP caching, and request analytics.
- **Content_Bucket**: The S3 bucket `crgomez-content` in `us-west-2`, created by this feature, with a dot-free name, ACLs disabled under `BucketOwnerEnforced`, and all four Public Access Block flags set at creation.
- **Origin_Endpoint**: The regional, non-dualstack, virtual-hosted-style S3 REST hostname `crgomez-content.s3.us-west-2.amazonaws.com`, which resolves to IPv4 addresses only.
- **Legacy_Bucket**: The existing S3 bucket `crgomez.com` in `us-west-2`.
- **Log_Bucket**: A separate S3 bucket created by this feature that receives S3 server access log records for Content_Bucket.
- **Legacy_State_Bucket**: The existing S3 bucket `crgomez.com-state` holding the pre-migration Terraform_AWS state object `crgomez/terraform.tfstate`.
- **S3_Service**: The Amazon S3 service as it evaluates authorization for and responds to requests addressed to Legacy_Bucket and Content_Bucket, including the HTTP status it returns to an anonymous caller.
- **Published_Document**: An object in Content_Bucket whose key is listed explicitly in the Content_Bucket policy Allow statement resource list.
- **Published_Resume**: The single Published_Document that Site links as the resume, sourced from the Legacy_Bucket object `crgomez-seceng-ir.pdf` and published under the Content_Bucket key `docs/resume.pdf`.
- **Canary_Object**: A permanent Content_Bucket object under the key `docs/access-canary.txt` with harmless content, deliberately never a Published_Document, used to prove that an existing unpublished object is refused to anonymous callers and remains readable by the owner.
- **Document_Path_Shape**: The key convention for Content_Bucket keys that are served through Delivery_Host. Keys use one of two prefixes: `docs/` for Published_Documents, comprising the resume and future published frameworks, together with the Canary_Object; and `img/` for site imagery, comprising the social-preview image and the favicon. The character and structure convention within a prefix is fixed by Requirement 14 criterion 4.
- **Retained_Objects**: The three Legacy_Bucket objects referenced by Site: `crgomez-security-engineer.pdf`, `hero-banner.png`, and `amplify.png`.
- **Unreferenced_Objects**: The six Legacy_Bucket objects that Site does not reference: `unpublished-variant-a.pdf` (this spec's neutral label for an unpublished role-targeted resume variant; the real object key contains a space character and is kept out of this spec), `crgomez-seceng-ir.pdf`, `IMG.png`, `city.png`, `patern.png`, and `snapseed.png`. Of these six, `crgomez-seceng-ir.pdf` is the Published_Resume source object and is retained under Requirement 2; the other five are deleted.
- **Site**: The static site in the public repository `crgomez/AmplifyAppResume`, deployed by AWS Amplify Hosting on push to `master` and served at `www.crgomez.com` through Cloudflare. Site files are `index.html`, `minimalist-sample.html`, and the files under `css/` and `js/`.
- **Cloud_Connector_Rule**: The Cloudflare Cloud Connector rule scoped to Delivery_Host that routes matching requests to Content_Bucket as an AWS S3 provider target and rewrites the `Host` header to the Origin_Endpoint automatically. Cloud Connector requires the Delivery_Host DNS record to be proxied, applies no caching of its own, is evaluated last in the request workflow, and takes precedence over other rules that modified the same settings, including the `Host` header.
- **Cache_Rule**: The Cloudflare cache rule scoped to Delivery_Host that sets edge caching behavior for Published_Document paths, required because Cloud_Connector_Rule applies no caching.
- **Terraform_AWS**: The Terraform configuration under `tf-files/` in the `AmplifyAppResume` repository, applied by AWS_Stack.
- **Terraform_Cloudflare**: The Terraform configuration in the private repository `crgomez/Terraform-CF-WAF`, applied by Cloudflare_Stack. Before the migration in Requirement 15, it is applied by Terraform Cloud workspace `terraform-cf-waf` through a GitHub Actions workflow running `terraform apply -auto-approve` on push to `main`.
- **Spacelift**: The Spacelift account and platform that hosts AWS_Stack and Cloudflare_Stack.
- **AWS_Stack**: The Spacelift stack that tracks repository `crgomez/AmplifyAppResume`, branch `master`, project root `tf-files/`, and applies Terraform_AWS.
- **Cloudflare_Stack**: The Spacelift stack that tracks repository `crgomez/Terraform-CF-WAF`, branch `main`, and applies Terraform_Cloudflare.
- **Tracked_Run**: A Spacelift run triggered by a commit to the tracked branch of a stack, which can apply changes after confirmation.
- **Proposed_Run**: A Spacelift plan-only run triggered by a pull request against the tracked branch of a stack, which cannot apply changes.
- **Plan_Role**: The IAM role, with read-only permissions, that AWS_Stack assumes through Spacelift's native AWS integration for planning.
- **Apply_Role**: The IAM role, limited to S3 actions on Legacy_Bucket, Content_Bucket, and Log_Bucket, that AWS_Stack assumes through Spacelift's native AWS integration for applying.
- **Spacelift_Context**: A Spacelift context holding environment variables, including write-only secret variables, attached to a named stack.
- **Change_Unit**: A single pull request on its own branch that is independently revertible and is verified before the next Change_Unit in Requirement 16 merges.
- **Operator procedure**: A delivery step in Requirement 16 that the Operator performs by CLI or console action rather than by merging a Change_Unit, such as the Phase 1 bootstrap, the Phase 2 content migration, and the branch protection configuration.
- **Phase 0**: The first delivery phase in Requirement 16, performed by AWS CLI with owner credentials outside the pipeline, comprising the Requirement 1 interim lockdown, the Requirement 2 deletions, and the first Negative_Access_Test run.
- **Phase 1**: The second delivery phase in Requirement 16, which sets up Spacelift, migrates both Terraform states, codifies the Phase 0 Legacy_Bucket configuration, and configures branch protection.
- **Phase 2**: The third delivery phase in Requirement 16, which provisions Content_Bucket and Log_Bucket, migrates content, applies the Content_Bucket policy and the Cloudflare delivery path, repoints Site, and applies the Legacy_Bucket final lockdown.
- **Branch protection**: The GitHub branch protection rules on `master` in `crgomez/AmplifyAppResume` and on `main` in `crgomez/Terraform-CF-WAF` that govern pull request merges, defined in Requirement 15.
- **Greptile**: The third-party code review service connected to the repository, whose pull request check stays advisory unless the owner makes it a required check under Requirement 15 criterion 26.
- **Range_Drift_Workflow**: The scheduled GitHub Actions workflow in `crgomez/AmplifyAppResume` that compares Cloudflare's published IPv4 list with the committed Cloudflare_Range_Allowlist.
- **Synthetic_Check**: The scheduled, unauthenticated GitHub Actions check of each Published_Document URL on Delivery_Host, which may run in the same workflow file as Range_Drift_Workflow.
- **Operator**: The repository owner, acting with authenticated AWS or Cloudflare credentials or by reviewing, merging, and confirming Change_Units and Spacelift runs.
- **Publish_Workflow**: The documented procedure an Operator follows to add a Published_Document or replace the content of an existing Published_Document, defined in Requirement 9.
- **Negative_Access_Test**: A scripted, fully unauthenticated acceptance test asserting that specific S3 and HTTP requests are refused.
- **Owner_Access_Check**: A scripted check, separate from Negative_Access_Test, that uses owner credentials to prove the bucket owner can still read an unpublished Content_Bucket object directly and through a presigned URL.
- **Public_Access_Block**: The S3 bucket-level configuration carrying the four flags `BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, and `RestrictPublicBuckets`.
- **Cloudflare_Range_Allowlist**: The reviewed literal list of IPv4 CIDR prefixes that Cloudflare publishes at `https://www.cloudflare.com/ips-v4` as the source addresses of its Edge origin fetches, committed in Terraform_AWS and used as the `aws:SourceIp` condition value in the Content_Bucket policy.
- **Scanner_Gate**: The acceptance condition applied to `checkov` and `trivy` output, defined in Requirement 13.

## Requirements

### Requirement 1: Interim lockdown of Legacy_Bucket without interrupting Site

**User Story:** As the site owner, I want anonymous enumeration of the existing bucket stopped immediately, so that the unpublished documents stop being discoverable before the longer migration finishes.

#### Acceptance Criteria

1. WHEN the interim Legacy_Bucket policy replacement completes, THE Operator SHALL set the Legacy_Bucket ACL to `private` and SHALL confirm that the resulting bucket ACL reports no grant to `http://acs.amazonaws.com/groups/global/AllUsers` and no grant to `http://acs.amazonaws.com/groups/global/AuthenticatedUsers`.
2. WHEN the pre-lockdown baseline capture and the Retained_Objects ownership confirmation both report success, THE Operator SHALL apply a Public_Access_Block configuration to Legacy_Bucket with `BlockPublicAcls` set to `true`, `IgnorePublicAcls` set to `true`, `BlockPublicPolicy` set to `false`, and `RestrictPublicBuckets` set to `false`, because `BlockPublicPolicy` set to `true` would reject the interim key-scoped policy and `RestrictPublicBuckets` set to `true` would suppress the anonymous `s3:GetObject` grant that Site still depends on.
3. WHEN the Legacy_Bucket Public_Access_Block configuration reports `IgnorePublicAcls` as `true`, THE Operator SHALL replace the Legacy_Bucket policy with a policy that grants `s3:GetObject` to `Principal: "*"` on exactly the three Retained_Objects key ARNs, grants no other action including no `s3:ListBucket` and no `s3:ListBucketVersions`, and names no other resource.
4. WHILE the interim Public_Access_Block configuration and the interim Legacy_Bucket policy are both in effect, THE S3_Service SHALL refuse anonymous `s3:ListBucket` and anonymous `s3:ListBucketVersions` requests against Legacy_Bucket with an HTTP 403 response, including requests that the bucket ACL `READ` grant to `http://acs.amazonaws.com/groups/global/AllUsers` would otherwise authorize.
5. WHEN the Operator begins the interim lockdown, and before any Legacy_Bucket configuration mutation is applied, THE Operator SHALL confirm that all three Retained_Objects report the bucket owner canonical ID as object owner, and SHALL stop the interim lockdown if any of the three reports a different owner, because anonymous access to objects owned by another account cannot be granted by the Legacy_Bucket policy alone.
6. WHEN each of the three Legacy_Bucket mutations completes, THE Operator SHALL verify by unauthenticated HTTPS request, with a 10-second response timeout and at most one retry per object, that each of the three Retained_Objects returns HTTP 200, that `Content-Type` is `application/pdf` for `crgomez-security-engineer.pdf` and `image/png` for `hero-banner.png` and `amplify.png`, and that the response body length is 482437 bytes, 1112252 bytes, and 15651 bytes respectively.
7. IF any Retained_Object fails verification at any of the three verification points, by returning a status other than HTTP 200, a `Content-Type` other than the expected value, or a body length other than the recorded size, THEN THE Operator SHALL restore the captured baseline Legacy_Bucket policy and ACL, SHALL re-run the verification against all three Retained_Objects, and SHALL record in the design document the mutation step in effect, the object key, the observed status, `Content-Type` and body length, the UTC timestamp, and the verification result after restoration, before continuing.
8. THE Operator SHALL apply the three Legacy_Bucket mutations in the order Public_Access_Block configuration first, policy replacement second, ACL set to `private` third, because the bucket ACL `READ` grant is the only authorization path for anonymous `s3:ListBucketVersions` and a single Public_Access_Block call with `IgnorePublicAcls` set to `true` suppresses it without altering the anonymous `s3:GetObject` authorization Site depends on; anonymous `s3:ListBucket` remains authorized by the pre-existing policy until the policy replacement completes.
9. WHEN the Operator begins the interim lockdown, and before any Legacy_Bucket configuration mutation is applied, THE Operator SHALL capture and store outside Legacy_Bucket the current Legacy_Bucket ACL grants, the current Legacy_Bucket policy document, and the observed absence of a Public_Access_Block configuration, so that the restoration path has a recorded pre-lockdown authorization state to return to.
10. THE Operator SHALL keep `crgomez-security-engineer.pdf` in Retained_Objects and SHALL issue no delete request against that key, because the deployed `index.html` links that key until Requirement 7 repoints Site.

### Requirement 2: Removal of unreferenced objects from Legacy_Bucket

**User Story:** As the site owner, I want the documents and images the site never links removed from anonymous reach, so that unpublished resume variants are no longer retrievable by anyone who guesses or recorded a key.

#### Acceptance Criteria

1. THE Operator SHALL delete each of the five Unreferenced_Objects recorded with disposition `delete` — `unpublished-variant-a.pdf`, `IMG.png`, `city.png`, `patern.png`, and `snapseed.png` — by issuing one delete request per key that names the object key and specifies no version ID, so that S3_Service creates a delete marker as the current version and retains the prior content as a noncurrent version, and SHALL pass the real key behind `unpublished-variant-a.pdf` as a single literal key value including its space character.
2. THE Operator SHALL issue the first delete request only after an authenticated read of Legacy_Bucket configuration, taken no more than 60 minutes earlier, reports versioning status `Enabled` and reports the Public_Access_Block flag `IgnorePublicAcls` from Requirement 1 as `true`, because a public object-version ACL can authorize a version-specific `GetObject` request independently of the bucket policy, and because a key-only delete against a bucket with versioning suspended destroys the prior content instead of retaining it.
3. WHEN the delete requests complete, THE Operator SHALL record the exact object key and the noncurrent version ID holding the prior content for each of the five deleted Unreferenced_Objects, taken from an authenticated listing of Legacy_Bucket object versions that shows a delete marker as the current version for each of those five keys and shows the real key behind `unpublished-variant-a.pdf` as one key rather than two, for use by the Negative_Access_Test in Requirement 11.
4. WHILE Legacy_Bucket reports `IgnorePublicAcls` as `true` and the Legacy_Bucket policy grants no `s3:GetObjectVersion` action, THE S3_Service SHALL refuse every anonymous `GetObject` request that specifies a recorded noncurrent version ID of an Unreferenced_Object, returning HTTP 403.
5. THE Operator SHALL record, before issuing any delete request, a disposition for each of the six Unreferenced_Objects, with `retain` recorded for `crgomez-seceng-ir.pdf` because that object is the Published_Resume source object required by Requirement 4, and with `delete` recorded for the other five, and SHALL rely on the Requirement 1 interim policy — which names only the three Retained_Objects — to keep the retained object outside anonymous reach.
6. THE Operator SHALL retain every noncurrent version created by this requirement for at least 90 days after its delete marker is created, SHALL issue no delete request specifying a version ID against Legacy_Bucket during that window, SHALL configure no Legacy_Bucket lifecycle rule that expires noncurrent versions during that window, and SHALL recover a deleted object by copying its recorded noncurrent version to the same key so that the prior content becomes current again.
7. IF an anonymous `GetObject` request specifying a recorded noncurrent version ID returns any status other than HTTP 403, THEN THE Operator SHALL issue no further delete requests, SHALL leave the already-created delete markers in place, and SHALL record the result as a failure of the safety argument stated in criterion 2, because soft deletion is sufficient only while no public object-version ACL is honored.
8. WHEN the Operator records the dispositions in criterion 5, and before any delete request is issued, THE Operator SHALL identify from an authenticated listing of Legacy_Bucket object versions every noncurrent version that predates this feature, and SHALL record the object key and version ID of each for use by the Negative_Access_Test in Requirement 11, because the pre-feature inventory reported 10 versions across 9 current objects, so at least one object already holds a noncurrent version.

### Requirement 3: Content_Bucket and Log_Bucket provisioning

**User Story:** As the site owner, I want a new bucket that starts private and cannot regress to the original finding, so that the fix is structural rather than a correction applied to a permissive default.

#### Acceptance Criteria

1. THE Operator SHALL create Content_Bucket in region `us-west-2` with the name `crgomez-content`, which contains no dot characters.
2. WHEN Content_Bucket is created, THE Operator SHALL set Content_Bucket object ownership to `BucketOwnerEnforced` in the same provisioning run, so that no ACL grant to `http://acs.amazonaws.com/groups/global/AllUsers` can be applied to Content_Bucket or to any object in it.
3. WHEN Content_Bucket is created, THE Operator SHALL apply in the same provisioning run a Public_Access_Block configuration with all four flags — `BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, and `RestrictPublicBuckets` — set to `true`, SHALL verify by reading the Public_Access_Block configuration back that all four flags report `true` before any object is written to Content_Bucket, and SHALL keep all four flags set to `true` for the lifetime of Content_Bucket with no exception path, which the IPv4-only `aws:SourceIp` condition in Requirement 5 criterion 3 permits because that condition is not evaluated as public.
4. THE Operator SHALL enable versioning on Content_Bucket and SHALL apply a Content_Bucket lifecycle configuration that permanently deletes a noncurrent object version 365 days after it becomes noncurrent while retaining the 5 most recent noncurrent versions of each key, so that version history does not grow without bound.
5. THE Operator SHALL enable default server-side encryption with `AES256` on Content_Bucket, so that every object written afterwards is encrypted at rest without a per-request encryption header.
6. THE Operator SHALL create Log_Bucket in region `us-west-2` in the same AWS account that owns Content_Bucket, with a name containing no dot characters, object ownership `BucketOwnerEnforced`, versioning enabled, default `AES256` encryption, and all four Public_Access_Block flags set to `true`.
7. THE Operator SHALL enable S3 server access logging on Content_Bucket with Log_Bucket as the destination and a non-empty key prefix that names Content_Bucket as the source and is used by no other logging destination configuration in Log_Bucket, and SHALL verify by reading the logging configuration back that the destination bucket and prefix match the values applied.
8. WHEN Content_Bucket exists, THE Operator SHALL verify by unauthenticated HTTPS request to `https://crgomez-content.s3.us-west-2.amazonaws.com/` that the TLS handshake completes with no certificate name-mismatch error and that an HTTP status response from S3 is returned rather than a connection or TLS failure, confirming that the dot-free name makes the virtual-hosted-style endpoint usable and that neither a path-style origin nor a URL-rewrite rule at the Edge is required.
9. THE Operator SHALL apply a Log_Bucket policy that grants `s3:PutObject` to the S3 logging service principal `logging.s3.amazonaws.com` on the Content_Bucket log prefix, conditioned on the source bucket being Content_Bucket and the source account being the account that owns Content_Bucket, because a `BucketOwnerEnforced` Log_Bucket cannot accept the legacy log-delivery group ACL grant.
10. THE Operator SHALL apply a Log_Bucket lifecycle configuration that expires objects under the Content_Bucket log prefix 90 days after creation, permanently deletes noncurrent versions of those objects 7 days after they become noncurrent, and removes expired object delete markers under that prefix with `ExpiredObjectDeleteMarker` set to `true`, so that neither log storage nor delete markers left by expiration accumulate without bound.
11. IF the create request for `crgomez-content` is refused because the name is already in use globally, THEN THE Operator SHALL select a replacement name that contains no dot characters and SHALL use the replacement name in every dependent configuration, including the Origin_Endpoint and the Apply_Role resource list, before provisioning continues.

### Requirement 4: Migration of retained content with explicit HTTP metadata

**User Story:** As the site owner, I want each copied object to carry a correct content type and an intentional cache lifetime, so that browsers and the Edge treat each document correctly without a query-string cache-buster.

#### Acceptance Criteria

1. THE Operator SHALL copy exactly three objects from Legacy_Bucket to Content_Bucket, each under the destination key given here, which follows Document_Path_Shape: `crgomez-seceng-ir.pdf` to `docs/resume.pdf` as Published_Resume, `hero-banner.png` to `img/hero-banner.png`, and `amplify.png` to `img/favicon.png`.
2. THE Operator SHALL record, before each copy, the source object size in bytes and a source content checksum, using `221604` bytes for `crgomez-seceng-ir.pdf`, `1112252` bytes for `hero-banner.png`, and `15651` bytes for `amplify.png`, so that the destination can be compared against a value captured independently of the copy operation.
3. THE Operator SHALL set `Content-Type` explicitly on each copied object to `application/pdf` for `docs/resume.pdf` and to `image/png` for `img/hero-banner.png` and `img/favicon.png`, rather than allowing the value to be inferred from the file extension by the copy tool.
4. THE Operator SHALL set `Cache-Control` explicitly on each copied object, with a `max-age` of 3600 seconds on `docs/resume.pdf` and a `max-age` of 604800 seconds on `img/hero-banner.png` and `img/favicon.png`, because Published_Resume is the object replaced by Publish_Workflow while the social-preview image and the favicon change rarely.
5. THE Operator SHALL set `Content-Disposition` explicitly on Published_Resume to disposition type `inline` with the `filename` parameter value `carlos-gomez-resume.pdf`, so that a download presents a human-readable filename that is independent of the stable `docs/resume.pdf` key.
6. WHEN a copy operation completes, THE Operator SHALL verify that the destination object size in bytes equals the recorded source size and that a destination content checksum computed with the same algorithm equals the recorded source checksum.
7. WHEN all three copy operations complete, THE Operator SHALL read back each destination object's stored `Content-Type` and `Cache-Control` values, and the stored `Content-Disposition` value on Published_Resume, and verify that each equals the value set in criteria 3, 4, and 5.
8. IF a destination size, checksum, or stored metadata value does not match the value required by criteria 3 through 6, THEN THE Operator SHALL re-copy the affected object with the metadata set explicitly, SHALL record the mismatch, and SHALL NOT treat the migration as complete until a subsequent verification of that object passes.
9. THE Operator SHALL accept that object version history does not transfer, because only current object content can be copied between buckets, and SHALL record that noncurrent versions of the copied objects exist only in Legacy_Bucket.
10. THE Operator SHALL retain Legacy_Bucket and the noncurrent versions Legacy_Bucket holds as a private archive.
11. ### Requirement 5: Key-scoped, origin-restricted Content_Bucket policy

1. 3. THE Content_Bucket policy SHALL condition the anonymous `s3:GetObject` grant on `aws:SourceIp` matching Cloudflare_Range_Allowlist, with the condition value containing every IPv4 prefix in Cloudflare_Range_Allowlist and no IPv6 prefix, because the Origin_Endpoint resolves to IPv4 addresses only and Edge origin fetches therefore arrive from IPv4 source addresses, and because Cloudflare's published IPv4 prefixes, `/13` through `/22`, are narrower than the `/8` bound at which AWS evaluates an `aws:SourceIp` condition as public, so the condition is used without transformation.

7. THE Content_Bucket policy SHALL include an explicit Deny statement that denies `s3:GetObject` and `s3:GetObjectVersion` to `Principal: "*"` with `NotResource` naming exactly the Published_Document key ARNs named in the Allow statement, conditioned on `StringEquals: { "aws:PrincipalType": "Anonymous" }` and referencing no account ID, so that a later statement naming a wildcard resource cannot make an unreferenced object anonymously readable while owner CLI access and owner-signed presigned URLs remain unaffected.

WHEN the Cloudflare delivery path Change_Unit in Requirement 16 has been applied, and before the Site Change_Unit merges, THE Operator SHALL purge one Published_Document URL at the Edge, SHALL retrieve that URL through the Edge, and SHALL require HTTP 200 with a body length equal to the stored object size, because an Edge-cached response would otherwise mask an origin refusal.

### Requirement 9: Publish and cache-invalidation workflow
